# Task 12 E2E pilot — RQ-0003

## 1. 対象

- RQ: `RQ-0003`
- final Investigation: `RQ-0003-v002`
- Question Type: `Methodological`
- Question: JSON Schema Draft 2020-12の条件付きvalidationで、単一の`30_analysis` schema内にQuestion Type別profileを安全に分離できるか？

## 2. E2E結果

Notion captureから以下を実施した。

1. Research QuestionをNotionへ登録
2. 公式JSON Schema specificationとproject schemaをSourcesへ登録
3. source-faithful Evidence Notesを作成
4. `00_context / 10_evidence / 20_synthesis / 30_analysis` をGitへ作成
5. `validate_investigation --through 30` でPASS
6. negative fixtureでprofile mismatchがFAILすることを確認
7. final Working AnswerをNotionへprojection

final canonical chain:

`30_analysis -> K0001–K0005 -> E0001–E0005 -> Notion Evidence Note -> Notion Source`

この経路でSourceまで逆引きできる。

## 3. Unknown / incomplete context

unknownを埋めるための架空defaultは使用しなかった。

`evidence_cutoff` は、このMethodological pilotではpublication-time boundaryとして意味を持たず、workflow中に生成するvalidator resultもEvidenceへ含めるため、final v002では設定しなかった。

## 4. Notionとの重複入力

意図的なsnapshotとして次は重複する。

- RQ Question / Question Type / Scope / Significance -> `00_context`
- selected Evidence Note text / type / locator -> `10_evidence`

ただしauthorityは二重化していない。

- current mutable RQ / Source / Evidence Note catalogはNotionが正本
- frozen Investigation snapshotはGitが正本
- Source bibliographic metadata一式はGitへ複製していない
- GitからNotionへのwrite-backはWorking Answerのみ

pilot上、不要なmanual duplicate inputは確認しなかった。

## 5. Finding

### F-01: formula型RQ IDをconnectorから直接取得できない

Notion connectorは `RQ ID` をactual valueではなく `formulaResult://...` として返した。

pilotではmetadataの「RQ UIDから自動生成」とcanonical `RQ-NNNN` contractから、`RQ UID = 3 -> RQ-0003` を決定論的に導出した。

Follow-up: Task 15。

### F-02: evidence_cutoffをfreeze timestampとして自動設定してはいけない

v001ではcontext freeze時刻を `evidence_cutoff` に設定した。

その後、workflow中に生成したvalidator resultをEvidenceへ含めるとcutoffを越えるため、frozen contextと矛盾した。

versioning ruleに従いv001をin-place修正せず、v002を作成した。

Follow-up: Task 16。

## 6. Schema評価

このpilotの範囲では、4 artifact schemaは過度に細かすぎるとは判断しなかった。

特に:

- unknownをnull / omissionで扱える
- `additionalProperties: false` によりartifact boundaryを保てる
- Question Type-specific `profile` のfield混入をnegative fixtureで拒否できる
- E -> K -> J lineageを表現できる

不足として確認したのはartifact fieldそのものより、`evidence_cutoff` の**運用意味論**である。
